# Bug Fix Playbook

의도한 동작과 실제 동작의 차이를 없애고 재발을 막는다. 요구사항 자체가 바뀌는 것이면 Feature다.

## 절차
1. **Main — 증상 정리:** 실제 결과, 기대 결과(근거: 결정 문서·코드·사용자), 재현 조건, 받은 로그·스택. 기대 결과가 불분명하면 사용자에게 묻는다.
2. **Tester — 선행 재현(기본):** Test 사이트에서 재현하고, 가능하면 **지금 실패하는 테스트**를 먼저 작성해 실패 출력을 증거로 남긴다. 원인 추측이나 수정은 하지 않는다.
   - **생략 가능(예외):** 스택 트레이스·로그·이미 실패하는 테스트 등 확실한 증거가 있을 때. Main은 생략 이유와 그 증거를 보고에 적는다. "명백해 보인다"만으로는 생략하지 않는다.
   - **재현 실패:** 로그 등으로 원인 증거가 충분하면 진행, 아니면 Investigation으로 전환한다. 불확실한 수정은 완료로 보고하지 않는다.
3. **Implementer — 원인 조사와 최소 수정:** Tester의 재현 결과(실패 테스트 경로·출력)만 받는다. 원인을 보고에 적는다. 관련 없는 정리는 하지 않는다.
4. **Main — 코드 동결.**
5. **Tester — 확인:** 2단계의 실패 테스트가 이제 통과하는지, 관련 기존 테스트, 변경 파일 Lint, UI 버그면 브라우저 확인.
6. **Main — 판정:** 수정 전 실패 → 수정 후 통과가 Tester 증거로 남았을 때 완료.

## 완료 조건
- 원래 증상이 Test 사이트에서 사라졌다는 Tester 증거.
- 가능하면 수정 전 실패하고 수정 후 통과하는 Tester 소유 회귀 테스트.
- 원인 설명(Implementer)과 미검증 범위.
