# Refactoring Playbook

외부에서 보이는 동작은 그대로 두고 내부 구조를 개선한다.

## 절차
1. **Main — 범위와 보존할 동작 정의:** 바꿀 코드, 개선 목표(중복 제거·가독성·성능 등), 바뀌면 안 되는 동작(반환값, DB 결과, 권한, 화면).
2. **Tester — 변경 전 기준 확보:** 코드를 바꾸기 전에 기준을 만든다. 방법은 Tester가 고른다.
   - 기존 테스트가 충분하면 그 실행 결과를 기준으로 쓴다.
   - 부족하면 입출력·DB 결과를 기록하는 테스트를 추가하거나, 같은 입력에 대한 결과를 파일로 남긴다.
   - 새 테스트 파일이 항상 필요한 것은 아니다. 무엇을 기준으로 삼았는지 보고한다.
3. **Implementer — 구조 개선:** Tester의 기준 확보가 끝난 뒤 수정한다(읽기·분석은 병렬 가능). 리팩터링 중 버그를 발견하면 **고치지 말고 Main에게 보고**한다. Main이 Bug Fix로 따로 처리할지 정한다.
4. **Main — 코드 동결.**
5. **Tester — 변경 후 같은 기준으로 비교:** 2단계와 같은 테스트·입력으로 결과가 같은지 확인. 변경 파일 Lint.
6. **Main — 판정:** 동작 보존(Tester 증거)과 의미 있는 개선(Main이 diff로 평가: 무엇이 얼마나 단순해졌는지)을 모두 만족해야 완료.

## 완료 조건
- 변경 전 기준과 변경 후 결과가 같다는 Tester 증거.
- 개선 효과에 대한 Main의 짧은 평가.
- 발견했지만 고치지 않은 버그 목록(있다면).
