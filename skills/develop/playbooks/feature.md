# Feature Playbook

신규 기능 또는 기존 기능의 업무 동작 변경. 작아도 저장·계산 규칙, 필드 의미, Link, 권한, Workflow가 바뀌면 여기다.

## 절차
1. **Main — 영향 조사:** 관련 DocType JSON, 컨트롤러, API, 기존 테스트, 결정 문서만 읽는다.
2. **Main — Grilling(필요할 때):** 데이터 관계·핵심 규칙·권한·기존 데이터 처리가 정해지지 않았으면 `grill` Skill. 명확하면 생략하고 이유를 한 줄 남긴다.
3. **Main — 진행 방식 선택:**
   - **병렬(기본):** DocType 여러 개, 새 규칙·권한, 경계 조건이 많은 경우.
   - **순차(예외):** 필드 하나·규칙 하나처럼 작고 분명한 경우. Implementer 완료 후 Tester.
   - 어느 쪽이든 Tester는 독립이다. 선택과 이유를 한 줄 남긴다.
4. **병렬일 때:** 같은 메시지에서 두 에이전트를 함께 호출한다.
   - Implementer: 구현.
   - Tester: **테스트 설계만**(정상·오류·경계·권한·회귀 목록과 확인 방법). 이 단계에서는 파일을 만들거나 고치지 않는다.
5. **Main — 코드 동결:** Implementer 완료 후 프로덕션 지문(develop §4).
6. **Tester — 테스트 코드 작성과 실행:** 병렬이었다면 앞의 설계를 넘겨 다시 호출한다(Codex는 같은 Tester에게 `send_message`/`followup_task`, Claude는 설계 결과를 브리프에 붙여 새 Tester 호출). Test 사이트 migrate → 테스트 코드 작성·실행 → 변경 파일 Ruff/ESLint → UI가 바뀌면 브라우저 확인.
7. **Main — 판정:** 지문 재확인. FAIL이면 Implementer에게 실패 내용만 넘겨 수정 → 동결 → Tester 재검증. 설계 충돌이면 사용자와 재합의 후 재위임.

## 규모 조절
- 필드 하나 추가: 그 DocType의 저장 동작, 필수·기본값, 목록·폼 표시.
- 여러 DocType 연결: 관계·정합성(삭제·취소 시), 권한, 기존 데이터, 회귀까지 넓힌다.

## 완료 조건
- 합의한 동작·예외·기존 규칙을 Tester가 Test 사이트에서 실제로 확인했다(테스트 코드 포함).
- 기존 데이터에 영향이 있으면 처리 방법(patch 등)과 그 검증.
- 미검증 범위를 숨기지 않는다.
